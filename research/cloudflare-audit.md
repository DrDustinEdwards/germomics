## 1. Config

Code (`wrangler.jsonc`): `compatibility_date` is `2026-06-21` (about 3.5 months old; stated only as a date, no policy). `nodejs_compat` is on. `observability` is `{ "enabled": true }` only: no `logs`/`traces` split and no `head_sampling_rate`. Logging is bare `console.error` with a string and the error object (`workers/app.ts:43`, `app/entry.server.tsx:24`), not structured JSON.

Vendor says (not verified): current compatibility date, observability with logs and traces and a stated sampling rate, structured JSON logs.

Recommendation, one PR: set `observability: { enabled: true, logs: { enabled: true, head_sampling_rate: 1 }, traces: { enabled: true, head_sampling_rate: 0.1 } }` (the rate is a DECIDE, below), bump the compatibility date after running the suite, and add a tiny `log(level, event, fields)` helper that writes `console.log(JSON.stringify(...))`, used at the two error sites. Risk: low; traces may count against plan limits. Bundle: negligible.

## 2. Env types

Code: `worker-configuration.d.ts` is generated by `wrangler types` and gitignored; `postinstall` and `typecheck` regenerate it. Good. The exception is `app/worker-secrets.d.ts`, which hand-declares five secrets (`BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `ADMIN_EMAIL`, `BETTER_AUTH_URL`), while `SENTRY_DSN` and `ANTHROPIC_API_KEY` are read through `env as unknown as { ... }` casts (`app/lib/sentry.server.ts:8`, `app/lib/ai.server.ts:46`). Those two are not typed at all.

Recommendation: declare `SENTRY_DSN?` and `ANTHROPIC_API_KEY?` in `worker-secrets.d.ts` and delete the casts. Wrangler can also list required secrets (`secrets.required` in newer versions) so types are generated; not verified for this wrangler version. Risk: none. Bundle: none.

## 3. Constant-time compare

Code: `app/lib/preview.server.ts:15-20` compares the preview token with a hand-written XOR loop. The unsubscribe token (`app/routes/unsubscribe.tsx`) is looked up in D1 by equality, which is a database comparison, not a secret compare against a stored hash.

Vendor says (per the job): `crypto.subtle.timingSafeEqual` over fixed-size hashes.

Recommendation: hash both strings with SHA-256 and compare with `crypto.subtle.timingSafeEqual`. The preview token is also the first 32 hex chars of an unkeyed `SHA-256(secret:preview:id)` with a hard-coded fallback secret (`"germomics-preview-secret"`) if `BETTER_AUTH_SECRET` is empty. An HMAC (`crypto.subtle.sign`) is the proper construction, and the fallback should be removed. Changing the construction invalidates existing preview links (they are regenerated on demand, so low impact). Risk: low. Bundle: smaller.

## 4. Lint, waitUntil, globals

Code: there is no ESLint config and no lint script or CI step. `ctx.waitUntil` is called as a method, never destructured (`app/lib/edge-cache.server.ts:160,171`, `app/lib/sentry.server.ts:78`): fine. `passThroughOnException` is not used. Module-level state: the CSP and header tables are constants; `RULES` is constant. I found no request-scoped state in module globals, but without a lint rule nothing keeps it that way. Unawaited promises: `captureException` returns void and schedules on `waitUntil`; the worker `fetch` awaits everything I read. Not exhaustively checked across 40 route files.

Recommendation: add ESLint with `@typescript-eslint/no-floating-promises` (needs type-aware linting against `tsconfig.cloudflare.json`) and run it in the existing `verify` job. First run will likely surface findings to triage. Risk: medium effort, no runtime risk. Bundle: none (dev only).

## 5. Bindings over REST

Code: D1, R2 (three buckets) and KV are all reached through bindings (`context.server.ts`). The only outbound `fetch` calls are Anthropic (`ai.server.ts:71`) and Sentry (`sentry.server.ts:66`), neither of which has a Cloudflare binding. Anthropic can be routed through AI Gateway, which is a Cloudflare product but not a binding replacement. Verified from code. No change.

## 6. Hand-written auth, SDKs

Code:
- Admin sign-in is Better Auth (`app/lib/auth.server.ts`), not hand-written JWT code. job_7e3fefd2f0db already plans Cloudflare Access with `jose`; that is the vendor-recommended replacement and removes the Better Auth tables, KV session storage and about 85 lines. Nothing to add here.
- Anthropic calls are a hand-written `fetch` with no retry or backoff (`ai.server.ts:66-100`). The vendor SDK would add retries and types at a cost in bundle size. It is a single-admin, low-volume path: not worth the bytes. Optional: a bounded retry on 429/529.
- Sentry is a hand-rolled store-endpoint POST (`sentry.server.ts`, 82 lines) that sends no stack frames beyond the first line. Cloudflare's own docs describe Sentry via `@sentry/cloudflare` (not verified). Workers Logs with traces may make Sentry unnecessary for a one-person site.

DECIDE A: keep the hand-rolled Sentry, move to `@sentry/cloudflare`, or drop Sentry and rely on Workers Logs. Recommendation: drop it once observability (item 1) is on, because it removes code and a secret.

## 7. Search

Code: the site uses D1 FTS5 (`posts_fts`, `content_blocks_fts`) queried from `posts.server.ts:160` and `content.server.ts:177`, with triggers in `drizzle/`. The corpus is one author's podcast and writing, tens to hundreds of rows.

Vendor says (not verified): AI Search (used by dustinedwards-info) and Vectorize are for semantic/RAG retrieval. For a keyword search over a small corpus, FTS5 in D1 is a supported and cheaper fit, and adds no bundle. Recommendation: keep FTS5. Revisit only if semantic search is wanted. The known cost is that FTS5 breaks `wrangler d1 export` (see CLAUDE.md backup section), which job_4ee9b2d33b50 addresses. No change.

## 8. Markdown, feeds, sitemaps, charts

Code: the podcast and site feeds are hand-built XML strings (`rss.server.ts`, 173 lines) with byte-level control the hard rules require (feed URL and guid never change). `sitemap.ts` and the discovery files (`discovery.server.ts`) are hand-written strings. There is no Markdown renderer in use (post bodies are sanitized HTML, `sanitize.server.ts`). Charts are Recharts, lazy loaded (`DataChart.client.tsx`).

Recommendation: do **not** swap the podcast feed generator for a library; hard rule 1 prizes exact output and the feed is the highest-risk surface. Feeds and sitemap are candidates for Prelum, and charts for Enarratio, only as part of the planned Capsomer move and only behind the existing feed diff script (`scripts/diff-feeds.mjs`). I could not read Prelum or Enarratio from this job, so I cannot say what they cover. DECIDE B: schedule that with the Capsomer design job.

## 9. Rate limiting

Code: `security.server.ts` implements a per-IP counter in KV (read, then put). The file says itself that it is not atomic and undercounts under burst. It also costs a KV read and write on every `/admin` request, and fixed 60 s windows are not enforced by Cloudflare.

Vendor says (per the job): the Workers Rate Limiting binding or WAF rules over KV counters; no single global Durable Object.

Recommendation: add `ratelimits` bindings (one each for ai, auth, admin) and replace `overLimit`. The per-minute limits are currently tunable live through the settings table, which a binding cannot do (limits are set in wrangler config), so this trades the live knob for an atomic counter. Also, once Access fronts `/admin` (job_7e3fefd2f0db), the `admin` and `auth` buckets mostly disappear and only `/admin/ai` and the daily AI cap remain. Recommendation: do this after the Access job, as a Dustin-reviewed config change. Needs a wrangler.jsonc binding: Dustin's step, not applied here. The AI daily cap (a UTC-day KV counter, `security.server.ts:150-166`) is a different thing (spend cap) and fine as is.

## 10. Static Assets, shared packages

No `@dustinedwards/*` shared packages are installed (`security-headers`, `rate-limit`, `site-helpers` would replace `security.server.ts` and parts of `edge-cache.server.ts`); I could not read them so I do not claim a fit. No Queues or Workflows are used; the only background work is `waitUntil` for cache refresh and Sentry, which is the right tool for that.

DECIDE C: adopt the shared `security-headers` and `rate-limit` packages when they are readable and germomics moves to Capsomer. Recommendation: yes, as part of that move, so the CSP and header table live in one place.
