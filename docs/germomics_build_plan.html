§ 01

Architecture & stack

Built from scratch as an independent, best-in-class project, benchmarked against the strongest modern podcast sites and chosen for one priority: a site that is native to Cloudflare, with no translation layer between the framework and the runtime.

  • Framework: React Router v7 (framework mode, TypeScript) + React 19, running on Cloudflare Workers through the official Cloudflare Vite plugin — first-class and native. D1, R2, KV and (later) Durable Objects are reached through bindings injected straight into every loader and action via context.cloudflare.env. No adapter, no Node shims, no cross-cloud HTTP.
  • Why not Next.js: Next runs on Cloudflare only via the OpenNext adapter — a translation layer that transforms a Vercel-shaped build to fit the Workers isolate. React Router v7 compiles directly to Web-standard Request/Response and executes in workerd as-is. For an all-Cloudflare build, native beats adapter.
  • Server / client separation: a route file co-locates its server loader/action and its client component. Server-only code (DB, secrets, auth) lives in *.server.ts modules so it can never leak into a client bundle.
  • Audio: Cloudflare R2 germomics-audio → media.germomics.com (public, CDN-cached, free egress). Filenames never change once published.
  • Images: R2 germomics-blog-images → images.germomics.com.
  • Data: Cloudflare D1 (SQLite) with Drizzle ORM — type-safe schema, migrations, clean queries; the live schema already exists.
  • Search: SQLite FTS5, across both content types.
  • Build & deploy: vite build then wrangler deploy; Workers Builds auto-detects React Router and wires CI/CD and preview deploys.
§ 02

Content model

One posts table with a single discriminator. An episode is a post with audio; a text entry is the same post without it.

Base fields

title, slug, body, excerpt, cover image, tags, status (draft/published), featured, SEO fields, version history, published date.

Discriminator

kind = episode | article — the one field that drives every listing, filter, and feed.

Episode-only fields

audio URL, duration, byte size, mime type, episode & season number, episode type (full/trailer/bonus), explicit flag, a permanent immutable guid, transcript, chapters (JSON), guests, and optional per-episode artwork.

Show config

title, description, author, owner email, artwork, Apple category, language, episodic/serial, subscribe links, funding URL.

§ 03

Sorting & information architecture

  • Home: one combined reverse-chronological feed; the player seeds with all episodes, newest first.
  • Sections: /episodes, /writing, a filterable /archive with tabs (all · episodes · writing), tag pages, guest pages, plus /data and /games.
  • Two feeds: a podcast feed (episodes only — every item carries audio) and a site feed for the writing. One discriminator, two queries.
§ 04

Persistent queue player

A single audio element in the root layout (app/root.tsx) with shared state, so it plays uninterrupted as the page changes around it. React Router does client-side navigation after hydration — only loader data moves over the wire — so the player tree is never unmounted between routes.

  • Episode page → plays that one episode. Home → plays the whole catalog, back to back.
  • Navigating never interrupts playback; pressing play swaps the queue; on end, advance to the next.
  • Skip ±15/30s, speed 0.8–2×, chapter jump-to, a clickable transcript synced to playback, share-at-timestamp, resume position, and Media Session API (lock screen, car, media keys).
§ 05

RSS & Podcasting 2.0

The podcast feed is served at /feed/podcast/ — the same path the old site uses — by a resource route: a route module with only a loader that returns a raw Response with Content-Type: application/xml. Byte-level control over every tag, no static-generation heuristics to fight.

  • iTunes channel + item tags (enclosure, permanent guid, duration, season/episode, episode type).
  • Podcast namespace: transcript, chapters (a JSON file, editable after publishing), person (hosts & guests), soundbite, funding, locked.
  • A separate site feed carries the writing for regular feed readers.
§ 06

Page features

  • Episode: header (number/season/duration/date), full show notes, chapter list, clickable synced transcript, guest bios, resource links, related episodes, subscribe-everywhere, share-at-timestamp.
  • Article: the same, without audio.
  • Subscribe page, newsletter capture, shareable soundbite clips, and a support/funding link.
  • Per-route meta() built from loader data drives titles, descriptions, and Open Graph tags — full SEO control, server-rendered.
§ 07

Data pages — maps & charts

Interactive pages about viruses and bacteria: outbreak maps, prevalence and timeline charts, genome and morphology visuals. These are client-side React, isolated cleanly from the edge runtime.

  • Maps: MapLibre GL (or Leaflet) rendered in a client-only boundary — map libraries need window, so they mount after hydration via clientLoader or a client-only wrapper.
  • Charts: a React charting library (Recharts / visx / D3) for graphs, distributions, and timelines.
  • Isolation: heavy viz libraries are lazy()-imported and code-split per route by Vite, so they never touch the blog or podcast bundles and never inflate the worker.
  • SEO shell: each data page still server-renders a real, crawlable landing (title, summary, meta) around the interactive canvas.
  • Source data: curated datasets in D1 (queried in the loader) or static JSON in R2; charts hydrate from loader data.
§ 08

Arcade games

Arcade-style browser games at /games — for example an outbreak-defense or phage-versus-bacteria game that ties into the microbiology content.

  • Engine: HTML canvas / WebGL via a lightweight engine (Phaser, PixiJS, or Kaplay) or a hand-rolled requestAnimationFrame loop, mounted in a client-only route component.
  • Code-split: each game ships only on its own route; the engine never loads on a content page.
  • Assets: sprites, sound effects, and any WASM blobs served from R2 over the CDN.
  • Leaderboards: high scores written to D1 through a route action.
  • Realtime (optional, later): Cloudflare Durable Objects + WebSockets for multiplayer rooms — native to the platform when wanted.
§ 09

Admin & publishing

A purpose-built, single-author editor — no multi-role machinery to maintain.

  • Audio upload straight to R2, with duration and byte size detected automatically.
  • Transcript field (paste or auto-generate), chapters editor, guest picker, episode/season numbers, explicit toggle, an auto-generated locked GUID.
  • Drafts, preview, publish, and version history.
  • Every admin route is gated behind a single allowlisted identity (see §11).
§ 10

Migration — zero disruption

The current feed lives on your own domain (germomics.com/feed/podcast/), so the directories already point at a URL you control.

  • The new site serves the feed at that same path — no need to touch Apple, Spotify, Amazon, Pandora, or TuneIn.
  • At build time, parse the existing feed and import each episode, preserving its original guid exactly — no duplicates, no reset.
  • Re-upload the MP3s to R2; keep the old media URLs alive through cutover; validate and diff the feeds before flipping hosting.
§ 11

Data layer & auth

  • D1 + Drizzle, native binding — a clean schema for this content model, queried in loaders and actions via drizzle(context.cloudflare.env.DB). No HTTP API. Time Travel gives always-on point-in-time backups to any minute in the recent window.
  • Auth: Better Auth — purpose-built for D1 + Drizzle on Workers. Sign in with Google, locked to one allowlisted admin address. A single catch-all route (app/routes/api.auth.$.ts) hands its loader and action to auth.handler(request).
  • Sessions: stored in a Cloudflare KV namespace (APP_KV); Better Auth adds a small set of tables to D1 (user, session, account, verification) via its Drizzle adapter. Trivial footprint for a single admin, and the idiomatic React-Router-on-Cloudflare pattern.

§ 13

Accessibility — WCAG 2.2 AA

Conformance target is WCAG 2.2 Level AA across the whole site. The commitments that actually shape the build:

  • Transcripts are required, not optional. Prerecorded audio needs a text alternative (SC 1.2.1), so every episode ships a transcript — which doubles as the SEO and reading win.
  • The player is the highest-risk surface. Full keyboard operation, a seek control that works without dragging (SC 2.5.7), names/roles/state on every control (SC 4.1.2), 24×24px minimum targets (SC 2.5.8), and a docked player that never hides the focused element (SC 2.4.11).
  • Interactive data & games need text equivalents. Maps and charts ship an accessible summary or data table; games carry clear instructions and keyboard controls where feasible, and are never the only path to information.
  • Contrast holds in both modes. Body, brand, and accent all clear 4.5:1 (UI/large 3:1). Light-mode cyan is #0E7490 for text — the brighter #0891B2 fell just short.
  • Sign-in is handled for free. The admin is private and single-user, so accessibility effort targets the public site; Google sign-in via Better Auth already satisfies SC 3.3.8.
  • Baseline floor: visible focus, reflow to 400% zoom, reduced motion respected, semantic landmarks, alt text on artwork.
